# 実機での測定の記録

Apple が文書化していない点を、iPhone の実機で測って確かめた記録である。
設計文書（[frames-and-units.md](../frames-and-units.md)、[time.md](../time.md)）は、この結果を前提にしている。

| 項目 | 値 |
| --- | --- |
| 測定日 | 2026-09-20 |
| 端末 | iPhone 16 Pro（`iPhone17,1`） |
| OS | iOS 26.7 |
| 方法 | アプリを起動引数 `-PocketSensorProbe` で起動し、12 秒のあいだセンサーの生値を 1 行 1 JSON で標準出力へ出した。Mac の `devicectl` の `--console` で受け取り、290 行を集計した |
| 端末の状態 | 縦持ちで、手で持ったまま。充電中で、熱の状態は nominal |

結果は、機種と OS の版に依存する可能性がある。
別の機種で確かめたときは、表を足す。

## 時計

同じ瞬間に読んだ 4 つの時計の値は、次のとおりだった。

| 時計 | 値（秒） |
| --- | --- |
| `CACurrentMediaTime()` | 54476.194423 |
| `ProcessInfo.systemUptime` | 54476.194423 |
| `mach_absolute_time`（秒へ換算） | 54476.194423 |
| `mach_continuous_time`（秒へ換算） | 60104.196393 |

前の 3 つは、互いの差が 1 µs に満たなかった。
`mach_continuous_time` は 5628 秒だけ進んでいて、この差は端末が起動してからスリープしていた時間に当たる。

各センサーのサンプルが届いた時点の `CACurrentMediaTime()` から、サンプルが持つ時刻を引いた値は、次のとおりだった。

| センサー | 時刻の出どころ | 件数 | 最小 | 中央値 | 最大 |
| --- | --- | --- | --- | --- | --- |
| ARKit | `ARFrame.timestamp` | 33 | 28.6 ms | 42.5 ms | 51.8 ms |
| 加速度 | `CMLogItem.timestamp` | 60 | 0.7 ms | 0.9 ms | 12.4 ms |
| ジャイロ | `CMLogItem.timestamp` | 60 | 0.8 ms | 0.9 ms | 17.4 ms |
| device motion | `CMLogItem.timestamp` | 60 | 1.1 ms | 1.3 ms | 24.8 ms |
| 気圧計 | `CMLogItem.timestamp` | 9 | 1592 ms | 1608 ms | 2735 ms |

どの差も正で小さい。
サンプルの時刻が `mach_continuous_time` の系統なら、差は -5628 秒になるはずである。
したがって、`ARFrame.timestamp` と `CMLogItem.timestamp` は、どちらも `mach_absolute_time` の系統である。

気圧計だけは、サンプルの時刻から 1.6 秒以上遅れて届く。
時計が違うのではなく、端末の中の処理に時間がかかっていると見られる。
届いた時点の時刻を付ける方式では、気圧に 1.6 秒以上の誤差が入ることになる。

## レート

| センサー | 設定 | 実測（1 秒ごとの集計の中央値） |
| --- | --- | --- |
| 加速度、ジャイロ、device motion | 100 Hz | 99.5 Hz |
| ARKit | 60 fps のフォーマット | 59.94 Hz |
| 気圧計 | 指定できない | 約 1 Hz（サンプルの間隔が 1.0 秒） |

ARKit の追跡は、219 フレーム目（開始から約 3.6 秒）で `limited`（初期化中）から `normal` に変わった。

## 加速度の符号

端末は縦持ちで、静止に近い状態だった。
このときの加速度の平均は (-0.122, -0.855, -0.479) G である。
同じあいだの `CMDeviceMotion.gravity` の平均は (-0.116, -0.858, -0.480) G、`userAcceleration` の平均は (-0.006, 0.007, 0.004) G である。

- 生の加速度は、`gravity` と `userAcceleration` の和に一致する
- `gravity` は地面の向き（端末の -y の側）を指している。静止した端末の比力は上を向くので、Core Motion の値は比力と逆向きである
- -9.80665 を掛けた値は (1.20, 8.39, 4.70) m/s² で、大きさは 9.69 m/s² になる
- この比力を `<name>_link` の座標へ写した向きは、ARKit のカメラ姿勢から求めた上向きと、中央値 0.97° の差で一致した（手持ちの揺れを含む）

## CMAttitude の四元数の向き

基準の座標系は `xArbitraryCorrectedZVertical`（z が鉛直の上向き）である。
`CMAttitude.quaternion` を q として、端末座標で表した `gravity` を q で回した結果を、基準の座標系での重力 (0, 0, -1) と比べた。

| q の解釈 | (0, 0, -1) との角度の差 |
| --- | --- |
| 端末座標から基準の座標系への回転（v_ref = q v_dev q⁻¹） | 60 サンプルすべてで 0.000° |
| 基準の座標系から端末座標への回転 | 中央値 120.4° |

`CMAttitude.quaternion` は、端末座標のベクトルを基準の座標系へ写す回転である。
`sensor_msgs/Imu` の `orientation` には、この値をそのまま入れる。

## カメラ座標と端末座標の軸の対応

ARKit のカメラ姿勢から、world の下向き (0, -1, 0) をカメラ座標で表した。
これを、Core Motion の `gravity`（端末座標）を軸の対応で写した結果と比べた。
追跡が落ち着いた 120 フレーム目以降の 19 組を使った。

| 軸の対応の候補（端末座標の v をカメラ座標へ） | 角度の差の中央値 | 最大 |
| --- | --- | --- |
| (-v_y, v_x, v_z) | 0.40° | 2.91° |
| (v_y, -v_x, v_z) | 121.7° | 136.0° |
| (v_x, v_y, v_z) | 75.9° | 82.6° |
| (-v_y, v_x, -v_z) | 58.3° | 66.8° |

1 行目が、[frames-and-units.md](../frames-and-units.md) に書いた対応（カメラの +x が端末の -y、+y が +x、+z が +z）である。
残る差は、カメラと IMU のサンプルの時刻のずれと、手持ちの揺れによる。
この対応を使うと、`<name>_link` と `<name>_imu_link` のあいだの回転は rpy で (0, -π/2, 0) になる。
実測の `gravity` をこの回転で写した結果も、軸の対応で写した結果と一致した。

- 端末を回したときの `imu/data` の yaw の符号
- 深度を RGB へ重ねたときの、輪郭の一致
