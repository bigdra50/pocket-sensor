# 実機での測定の記録

Apple が文書化していない点を、iPhone の実機で測って確かめた記録である。
設計文書（[frames-and-units.md](../frames-and-units.md)、[time.md](../time.md)）は、この結果を前提にしている。

| 項目 | 値 |
| --- | --- |
| 測定日 | 2026-09-20 |
| 端末 | iPhone 16 Pro（`iPhone17,1`） |
| OS | iOS 26.7 |
| 方法 | アプリを起動引数 `-PocketSensorProbe` で起動し、12 秒のあいだセンサーの生値を 1 行 1 JSON で標準出力へ出した。Mac の `devicectl` の `--console` で受け取り、290 行を集計した |
| 端末の状態 | 縦持ちで、手で持ったまま。充電中で、熱の状態は nominal |

結果は、機種と OS の版に依存する可能性がある。
別の機種で確かめたときは、表を足す。

## 時計

同じ瞬間に読んだ 4 つの時計の値は、次のとおりだった。

| 時計 | 値（秒） |
| --- | --- |
| `CACurrentMediaTime()` | 54476.194423 |
| `ProcessInfo.systemUptime` | 54476.194423 |
| `mach_absolute_time`（秒へ換算） | 54476.194423 |
| `mach_continuous_time`（秒へ換算） | 60104.196393 |

前の 3 つは、互いの差が 1 µs に満たなかった。
`mach_continuous_time` は 5628 秒だけ進んでいて、この差は端末が起動してからスリープしていた時間に当たる。

各センサーのサンプルが届いた時点の `CACurrentMediaTime()` から、サンプルが持つ時刻を引いた値は、次のとおりだった。

| センサー | 時刻の出どころ | 件数 | 最小 | 中央値 | 最大 |
| --- | --- | --- | --- | --- | --- |
| ARKit | `ARFrame.timestamp` | 33 | 28.6 ms | 42.5 ms | 51.8 ms |
| 加速度 | `CMLogItem.timestamp` | 60 | 0.7 ms | 0.9 ms | 12.4 ms |
| ジャイロ | `CMLogItem.timestamp` | 60 | 0.8 ms | 0.9 ms | 17.4 ms |
| device motion | `CMLogItem.timestamp` | 60 | 1.1 ms | 1.3 ms | 24.8 ms |
| 気圧計 | `CMLogItem.timestamp` | 9 | 1592 ms | 1608 ms | 2735 ms |

どの差も正で小さい。
サンプルの時刻が `mach_continuous_time` の系統なら、差は -5628 秒になるはずである。
したがって、`ARFrame.timestamp` と `CMLogItem.timestamp` は、どちらも `mach_absolute_time` の系統である。

気圧計だけは、サンプルの時刻から 1.6 秒以上遅れて届く。
時計が違うのではなく、端末の中の処理に時間がかかっていると見られる。
届いた時点の時刻を付ける方式では、気圧に 1.6 秒以上の誤差が入ることになる。

## レート

| センサー | 設定 | 実測（1 秒ごとの集計の中央値） |
| --- | --- | --- |
| 加速度、ジャイロ、device motion | 100 Hz | 99.5 Hz |
| ARKit | 60 fps のフォーマット | 59.94 Hz |
| 気圧計 | 指定できない | 約 1 Hz（サンプルの間隔が 1.0 秒） |

ARKit の追跡は、219 フレーム目（開始から約 3.6 秒）で `limited`（初期化中）から `normal` に変わった。

## 加速度の符号

端末は縦持ちで、静止に近い状態だった。
このときの加速度の平均は (-0.122, -0.855, -0.479) G である。
同じあいだの `CMDeviceMotion.gravity` の平均は (-0.116, -0.858, -0.480) G、`userAcceleration` の平均は (-0.006, 0.007, 0.004) G である。

- 生の加速度は、`gravity` と `userAcceleration` の和に一致する
- `gravity` は地面の向き（端末の -y の側）を指している。静止した端末の比力は上を向くので、Core Motion の値は比力と逆向きである
- -9.80665 を掛けた値は (1.20, 8.39, 4.70) m/s² で、大きさは 9.69 m/s² になる
- この比力を `<name>_link` の座標へ写した向きは、ARKit のカメラ姿勢から求めた上向きと、中央値 0.97° の差で一致した（手持ちの揺れを含む）

## CMAttitude の四元数の向き

基準の座標系は `xArbitraryCorrectedZVertical`（z が鉛直の上向き）である。
`CMAttitude.quaternion` を q として、端末座標で表した `gravity` を q で回した結果を、基準の座標系での重力 (0, 0, -1) と比べた。

| q の解釈 | (0, 0, -1) との角度の差 |
| --- | --- |
| 端末座標から基準の座標系への回転（v_ref = q v_dev q⁻¹） | 60 サンプルすべてで 0.000° |
| 基準の座標系から端末座標への回転 | 中央値 120.4° |

`CMAttitude.quaternion` は、端末座標のベクトルを基準の座標系へ写す回転である。
`sensor_msgs/Imu` の `orientation` には、この値をそのまま入れる。

## カメラ座標と端末座標の軸の対応

ARKit のカメラ姿勢から、world の下向き (0, -1, 0) をカメラ座標で表した。
これを、Core Motion の `gravity`（端末座標）を軸の対応で写した結果と比べた。
追跡が落ち着いた 120 フレーム目以降の 19 組を使った。

| 軸の対応の候補（端末座標の v をカメラ座標へ） | 角度の差の中央値 | 最大 |
| --- | --- | --- |
| (-v_y, v_x, v_z) | 0.40° | 2.91° |
| (v_y, -v_x, v_z) | 121.7° | 136.0° |
| (v_x, v_y, v_z) | 75.9° | 82.6° |
| (-v_y, v_x, -v_z) | 58.3° | 66.8° |

1 行目が、[frames-and-units.md](../frames-and-units.md) に書いた対応（カメラの +x が端末の -y、+y が +x、+z が +z）である。
残る差は、カメラと IMU のサンプルの時刻のずれと、手持ちの揺れによる。
この対応を使うと、`<name>_link` と `<name>_imu_link` のあいだの回転は rpy で (0, -π/2, 0) になる。
実測の `gravity` をこの回転で写した結果も、軸の対応で写した結果と一致した。

## 配信の全経路での確認

アプリから WiFi 経由で Python SDK へ配信し、受け取ったデータで整合を確かめた。
端末は手で持って動かしている状態で、購読したのは RGB（15 Hz）、深度（15 Hz）、姿勢（30 Hz）、IMU（100 Hz）である。

| 項目 | 結果 |
| --- | --- |
| `open` にかかった時間 | 0.32 秒（`device_info`、`tf_static`、最初の `camera_info` を待つ時間を含む） |
| フレームの組のレート | 13.4 Hz から 16.0 Hz |
| 姿勢のレート | 27 Hz から 28 Hz |
| IMU のレートとサンプルの間隔 | 100 Hz、中央値 10.06 ms、最大 10.1 ms |
| 計測から SDK への到着までの遅延 | 中央値 107 ms、95 パーセンタイル 181 ms |
| 時計合わせの往復の時間 | 5.95 ms |
| iPhone と Mac の壁時計の差 | -43 ms |
| RGB の JPEG の大きさ（960×720、品質 0.8） | 約 78 KB |
| 5 秒の記録（RGB、深度、姿勢、IMU）の MCAP の大きさ | 1.5 MB（チャンクを圧縮した状態） |

座標の変換は、受け取ったデータで次のように確かめた。

| 検算 | 結果 |
| --- | --- |
| `<name>_link` の座標で表した、ARKit の上向きと `CMAttitude` の上向きの角度の差 | 106 組の中央値 0.39°、最大 4.15° |
| 静止に近いサンプルだけを選んだときの、比力の向きと ARKit の上向きの角度の差 | 16 組の中央値 0.81° |
| 比力の大きさ | サンプルごとの平均 9.86 m/s² |

1 行目の検算は、ARKit の姿勢の変換、`<name>_link` から `<name>_imu_link` への固定の変換、`CMAttitude` の向きがすべて正しいときにだけ一致する。
端末の動きによる加速度には左右されない。

内部パラメータは、probe のときの fx = 1367.56 に対して、この測定では 1343.5 相当（960 画素幅で 671.77）だった。
被写体までの距離が変わってオートフォーカスが働いたためと見られる。
`camera_info` をフレームごとに送る設計の根拠になる。

parameters と services も、実機で動作を確かめた。
`color.rate` を 15 から 5 へ変えると、実測のレートは 16.0 Hz から 5.5 Hz へ下がった。
`reset_origin` を呼ぶと `origin_epoch` が 1 へ増え、姿勢が原点へ戻った。

## 表示ツールの側のクライアントでの確認

Lichtblick と Foxglove が内部で使うパッケージ（`@foxglove/ws-protocol`、`@foxglove/rosmsg`、`@foxglove/rosmsg2-serialization`）で、実機へ接続した。
検査のスクリプトは `tools/foxglove-client-check/` にある。

| 項目 | 結果 |
| --- | --- |
| 接続と `serverInfo` | `foxglove.websocket.v1` でつながり、`cdr` と 3 つの capability が広告された |
| スキーマの解析 | 広告された 18 チャンネルのすべてで、`ros2msg` のスキーマを解析できた |
| メッセージの復号 | GNSS を除く 16 チャンネルで、8 秒のあいだに届いた全メッセージを復号できた |
| `header.stamp` | どのチャンネルでも、メッセージに付いた時刻と一致した |
| `clock_sync` | `t1` がそのまま返り、`t2` は `t3` より後にならなかった |
| parameters | 読み出しと、`color.rate` の書き換えができた |

GNSS の 2 チャンネルには、何も届かなかった。
`/diagnostics` の `pocketsensor/gnss` は `not_determined` を示しており、位置情報の許可のダイアログに答えていないことが原因だった。

## WiFi での破棄

全チャンネルを購読した状態の `/diagnostics` は、次の値を示した。
熱の状態は nominal だった。

| チャンネル | 設定のレート | 送った実績 | 背圧で捨てた数（セッションの開始からの累計） |
| --- | --- | --- | --- |
| 姿勢、`tracking`、`/tf` | 30 Hz | 27.0 Hz | 60 |
| 深度、confidence、`depth/camera_info` | 15 Hz | 14.0 Hz | 20 |
| RGB、`color/camera_info` | 6.7 Hz（`color.rate` は 7） | 5.5 Hz | 24 |
| IMU（融合値と生値） | 100 Hz | 99.5 Hz | 0 |
| 地磁気 | 50 Hz | 49.5 Hz | 0 |

最新 1 件を保持する背圧のチャンネルだけが、設定より 1 割ほど低い。
送り終わる前に次のフレームが来て、古いほうが捨てられている。
上限付きのキューを使う IMU は、欠けていない。
無圧縮の深度と confidence が合わせて毎秒 2.2 MB あり、WiFi ではこれが帯域の大半を占める。

## 深度を PNG にしたときの大きさ

PNG のチャンネルと無圧縮のチャンネルを実機から同時に受け取り、54 フレームで比べた。
場面は物のある室内で、深度は 0.20 m から 1.56 m、値の種類は 1 フレームに約 1,400 だった。

| 対象 | 無圧縮 | PNG（中央値） | 比 |
| --- | --- | --- | --- |
| 深度（`16UC1`、256×192） | 98,384 バイト | 27,046 バイト | 3.6 分の 1 |
| confidence（`mono8`、256×192） | 49,232 バイト | 3,663 バイト | 13.4 分の 1 |

大きさは CDR のメッセージ全体の値である。
15 Hz では、毎秒 2.21 MB が 0.46 MB になる。
同じ時刻のフレームどうしで、PNG を復号した画素は無圧縮の画素とすべて一致した。
`format` の文字列と、深度の 12 バイトのヘッダも、仕様のとおりだった。

場面が単純だと、比はもっと大きくなる。
0.39 m から 0.50 m の平らな面だけを映した記録では、深度が 10.6 分の 1（9,254 バイト）になった。

confidence の値の割合は、この場面で 0（低）が 18 %、1（中）が 33 %、2（高）が 49 % になった。
平らな面だけを映した記録では、全画素が 0 である。
その記録では追跡も、特徴の不足による制限ありの状態が続いていた。

符号化にかかる時間を Mac で測ると、深度が 0.40 ms、confidence が 0.18 ms になる（ImageIO、256×192、50 回の中央値）。

### WiFi での効果

同じ場所で、無圧縮と PNG を 12 秒ずつ交互に 2 回ずつ測った。
購読したのは RGB（15 Hz）、深度と confidence（15 Hz）、姿勢（30 Hz）、IMU（100 Hz）である。

| 項目 | 無圧縮（1 回目、2 回目） | PNG（1 回目、2 回目） |
| --- | --- | --- |
| フレームの組のレート | 12.2 Hz、11.1 Hz | 13.8 Hz、15.1 Hz |
| 遅延の中央値 | 153 ms、140 ms | 110 ms、75 ms |
| 遅延の 95 パーセンタイル | 251 ms、241 ms | 183 ms、149 ms |
| 捨てた姿勢 | 91、100 | 23、0 |
| 捨てた深度 | 33、44 | 14、0 |
| 捨てた RGB | 28、35 | 5、0 |

PNG にすると、深度だけでなく、同じ接続を通る姿勢と RGB の破棄も減る。
受け手 SDK と ROS 2 の中継が、端末の広告を見て PNG のほうを購読するのは、この結果による。

## USB での配信

Mac 本体のポートへケーブルで直結し、SDK の `usb:` で接続した。
SDK が usbmuxd と直接話すので、`iproxy` でポートを転送する手順は要らない。
購読したのは WiFi の測定と同じで、RGB（15 Hz）、深度と confidence（15 Hz）、姿勢（30 Hz）、IMU（100 Hz）である。

| 項目 | USB | WiFi（同じ日の測定） |
| --- | --- | --- |
| `open` にかかった時間 | 0.11 秒 | 0.32 秒 |
| フレームの組のレート | 15.1 Hz | 無圧縮で 11 Hz から 12 Hz、PNG で 14 Hz から 15 Hz |
| 姿勢、RGB、深度の送った実績 | 30.0 Hz、15.0 Hz、15.0 Hz | 無圧縮では 1 割から 2 割低い |
| 遅延の中央値 | 57 ms から 69 ms | 無圧縮で 140 ms から 153 ms、PNG で 75 ms から 110 ms |
| 遅延の 95 パーセンタイル | 62 ms から 74 ms | 無圧縮で 241 ms から 251 ms、PNG で 149 ms から 183 ms |
| 背圧で捨てた数（12 秒の窓を 4 回） | 0 | 無圧縮では、姿勢だけで 1 回に 90 から 100 |
| 時計合わせの往復の時間 | 0.85 ms | 5.95 ms |

USB では、無圧縮でも PNG でも結果が変わらなかった。
遅延の中央値と 95 パーセンタイルの差は 5 ms ほどで、WiFi の 100 ms 前後に比べて揺れが小さい。
残る 60 ms の大半は、ARKit が ARFrame を渡すまでの遅れ（29 ms から 52 ms）である。

全ストリーム（地磁気、気圧、GNSS、電池、IMU の生値を含む）を 20 秒受けたときの IMU は、次のとおりだった。

| 項目 | 融合値 | 生値 |
| --- | --- | --- |
| 受け取った数 | 1,994 | 1,994 |
| サンプルの間隔の中央値と最大 | 10.05 ms、10.06 ms | 10.05 ms、10.06 ms |
| 15 ms を超える間隔、重複 | 0、0 | 0、0 |

## GNSS

位置情報を許可した状態では、購読から 0.2 秒で最初の測位が届いた。
屋内で、水平の精度は 5.9 m、垂直の精度は 30 m だった。
`status` は `STATUS_FIX`、`service` は仕様のとおり 0 である。

`time_reference` が運ぶ GNSS の時刻と、同じ測位の `header.stamp` の差は -1.6 ms だった。
`header.stamp` は、センサーの時計の値を `anchor` で壁時計へ写したものである。
独立に得た 2 つの時刻が合っているので、`anchor` の計算が正しいことの裏付けになる。

## Lichtblick の画面での表示

Lichtblick の Web 版（Docker の `ghcr.io/lichtblick-suite/lichtblick`）を Chrome で開き、接続の種類に Foxglove WebSocket を選んで、擬似デバイスと実機の両方へ直接つないだ。

| パネル | 結果 |
| --- | --- |
| トピックの一覧 | 全チャンネルが、スキーマの名前と一緒に並んだ |
| 3D | `/tf` と `/tf_static` から、`odom`、`link`、光学 frame、IMU、anchor の木が描かれた |
| Image（`color/image/compressed`） | JPEG が表示された。実機では、カメラの映像がそのまま出た |
| Image（`depth/image`） | `16UC1` の深度として認識され、値の範囲を指定すると濃淡で表示された。較正には `depth/camera_info` が自動で選ばれた。範囲を指定しないと 0 mm から 10000 mm の固定になり、0.2 m から 2.9 m の場面はほぼ真っ黒に見えた |
| Image（`depth/confidence/compressed`） | PNG が復号された。値が 0 から 2 なので、見た目はほぼ黒い |
| Image（`depth/image/compressedDepth`） | 復号できなかった（`Error decoding image`）。先頭の 12 バイトのヘッダを、Lichtblick は読み飛ばさない |
| Raw Messages（`imu/data`） | `linear_acceleration.z` が 9.80665 と表示された |

`examples/lichtblick-layout.json` は、深度の色と値の範囲を設定済みのレイアウトである。
URL の `layoutUrl` にこのファイルの場所を渡すと、実機の深度が色付きで表示された。

アラートは 2 種類出たが、どちらも案内で、復号の失敗ではなかった。
60 Hz を超えるトピックがあること（IMU の 100 Hz）と、TF の先読みの設定を勧めるものである。

## ROS 2 の上での確認

ROS 2 Jazzy のコンテナの中で中継をビルドして動かし、`ros2/docker/` のスクリプトで確かめた。
相手は、擬似デバイスと実機（WiFi）の両方である。

| 確かめたこと | 結果 |
| --- | --- |
| `colcon build` | `pocketsensor_msgs` と `pocketsensor_ros` がビルドできた |
| xacro | マクロを展開した URDF を `check_urdf` が読み、`base_link` の下に 3 つの link が並んだ |
| トピックの型とレート | rclpy のノードで、標準の型と `TrackingStatus` を受け取れた。擬似デバイスでは、姿勢 29.8 Hz、IMU 98 Hz、深度 14.7 Hz |
| `header.stamp` | ROS の時計との差は、擬似デバイスで 1 ms から 25 ms、実機の WiFi で 45 ms から 220 ms（計測から届くまでの遅延に当たる） |
| TF | `odom` から `link`、`link` から光学 frame と IMU、`odom` から anchor が引けた。`publish_tf:=false` では `link` から anchor だけが出た |
| 深度の PNG | `image_transport` の `republish` が、`compressedDepth` を `16UC1` の 256×192 へ、`compressed` を `mono8` へ戻した |
| rosbag2 | SDK が実機から記録した MCAP を `ros2 bag info` が読み、`ros2 bag play` の再生を `ros2 topic echo` で受け取れた |

実際に動かして、不具合が 3 つ見つかった。

- `package.xml` の保守者のメールアドレスを catkin の検証が不正と判定し、ビルドが止まる
- 終了のシグナルを受けた中継が、例外を出して終わる
- 記録の先頭に、セッションの開始からの無音ができる

3 つ目は、アプリを起動して 4 分後に 3 秒だけ記録した bag の長さが 278 秒になる、という形で現れた。

## 深度と RGB の重なり

深度の画素と RGB の画素が同じ場所を指しているかを、WiFi で受け取った 1 組のフレーム（RGB 960×720、深度 256×192）で確かめた。
端末は机へ置いたままで、映っていた物までの距離は 0.09 m から 0.38 m だった。

深度が隣の画素と 8 % 以上違う所を輪郭とみなし、3.75 倍（960/256）に拡大して RGB へ重ねた。
輪郭は、手前の物の縁とケーブルに沿って並んだ。

重なりの度合いは、輪郭の上での RGB の明るさの勾配の平均で測った。
輪郭を上下左右へ 1 画素ずつずらし、この値が最大になるずれを探した。
画像全体での勾配の平均は 3.0 である。

| 画像の範囲 | 輪郭の画素数 | 値が最大になるずれ（RGB の画素） | 最大の値 | ずらさないときの値 |
| --- | --- | --- | --- | --- |
| 中央（x が 320 から 640） | 7,436 | 左へ 4、上へ 2 | 16.7 | 13.6 |
| 右（x が 640 以上） | 2,188 | 左へ 4 | 20.2 | 14.9 |

ずれは深度の 1 画素（RGB の 3.75 画素）ほどで、中央と右端で同じだった。
このうち約 2 画素は測り方に由来する。
輪郭を、不連続をはさむ 2 画素のうち右と下の側へ置いたためである。

倍率が合っていなければ、ずれは画像の端へ向かって大きくなる。
中央と右端でずれが同じなので、深度の内部パラメータを RGB の 256/960 倍として求める換算は合っていると判断した。

画像の左側には平らな画面しか映っておらず、輪郭が無かったので確かめていない。

## 端末を動かしたときの軸と符号

`pocketsensor check-axes` の指示に従って、端末を手で動かした。
持ち方はカメラ群を上にした横置きで、接続は WiFi である。
位置の変化は、動かし始めたときの `<name>_link` の座標で表している。

| 動かし方 | 測った値 | 約束 |
| --- | --- | --- |
| 静止 | 比力の大きさ 9.824 m/s²、`<name>_link` の上向きとの角度の差 0.2°、位置のずれ 2.1 cm | 比力は上を向き、大きさは 9.8 m/s² |
| 背面カメラの向く方向へ動かす | (+0.503, -0.014, +0.039) m | x が増える |
| 左へ動かす | (-0.165, +0.598, -0.061) m | y が増える |
| 上へ動かす | (-0.000, -0.105, +0.628) m | z が増える |
| 上から見て反時計回りに回す | 姿勢の yaw が +10.2°、`imu/data` の向きから求めた yaw が +10.9° | どちらも増える |
| 前へすばやく押し出す | 動き出しから 150 ms のあいだの、`<name>_link` の x の加速度のピークが +3.71 m/s² | 正になる |

どの動きでも、軸と符号は [frames-and-units.md](../frames-and-units.md) の定義のとおりだった。
回す動きは角度が小さく、`check-axes` の判定の下限（20°）に届かなかったので、この手順の判定は保留と表示された。
ARKit の姿勢と IMU という独立した 2 つの出どころが、同じ符号で 0.7° の差に収まっているので、符号は合っていると判断した。
別の回では、姿勢の yaw が +22.8° まで増えている。

## 熱によるレートの低下

1 時間以上にわたって起動と配信を繰り返したあと、`/diagnostics` の `pocketsensor/thermal` が `serious` を示した。
このとき、RGB と深度は 15 Hz の設定に対して 7.0 Hz、`/tf` は 30 Hz の設定に対して 16 Hz（anchor の分を含む）で送られていた。
[protocol.md](../protocol.md) に定めた、serious で上限の半分へ下げる動作のとおりである。
IMU のレートは 100 Hz のままだった。

同じ時点で、WiFi の接続が 3 つあり、そのうちの 1 つは無圧縮の深度を購読していた。
受け手 SDK でのフレームの組は 3.8 Hz まで下がった。
フレームの組は、同じ時刻の RGB と深度の両方が届いたときにだけ成立する。
それぞれが 7 Hz へ減り、さらに背圧で別々に捨てられるので、組の成立する回数は 7 Hz よりも大きく下がる。

そのあと 17 分のあいだ、`/diagnostics` を 1 分おきに読んだ。

| 時点 | 熱の状態 | RGB と深度を送った実績 |
| --- | --- | --- |
| アプリが 7 分のあいだ背景にいた直後 | `fair` | 11.0 Hz |
| 配信を再開して 1 分後 | `serious` | 4.0 Hz |
| 再開して 5 分後から 9 分後 | `serious` | 3.5 Hz から 0.5 Hz |

ARKit を止めて 7 分置くと `fair` まで下がるが、配信を再開すると 1 分で `serious` へ戻った。
`serious` のあいだの実績は、上限の半分（7.5 Hz）よりさらに低い。
間引きは、ARKit のフレームが毎秒 60 枚届く前提で、フレームの枚数を数えて行っている。
熱で ARKit のフレームの数そのものが減ると、実績はその分だけ設定より下がる。
これが原因かどうかは、ARKit のフレームの数を同時に測っていないので確かめていない。

## 購読に応じたセンサーの起動と停止

アプリを、画面の表示をすべて OFF にする起動引数（`-PocketSensorDisplayOff`）で起動した。
WiFi でつなぎ、購読を 1 つずつ変えながら `/diagnostics` の `pocketsensor/sensors` を読んだ。

| 操作 | 結果 |
| --- | --- |
| 何も購読しない | 全センサー群が `off`。`pocketsensor/tracking` は OK で、`message` は `stopped` |
| `odom` と `tracking` を購読する | ARKit だけが `on` になった。最初の `odom` は、購読から 0.93 秒で届いた |
| 深度（PNG）を購読する | 深度が `on` になり、最初の深度は 1.15 秒で届いた。`origin_epoch` は 0 のまま |
| 深度の購読をやめる | 4 秒後はまだ `on` で、10.7 秒後に `off` になった。ARKit は動いたままで、`origin_epoch` も 0 のまま |
| `imu/data` を購読する | IMU が `on` になった |
| すべての購読をやめる | 11.1 秒後に、ARKit と IMU が `off` になった |
| もう一度 `odom` を購読する | ARKit が動き直し、`origin_epoch` が 1 へ増えた |

全センサーが止まった状態から、受け手 SDK で RGB、深度、姿勢、IMU を開いた。
`open` は 0.81 秒で戻り、最初のフレームの組も接続から 0.81 秒で届いた。
続く 8 秒のレートは、フレームの組が 15.1 Hz、IMU が 107 Hz だった。

この測定の直前、センサーを止めた状態で数分置くと、熱の状態は `serious` から `nominal` まで戻っていた。
センサーを止めることでどれだけ発熱が減るかは、条件を揃えた比較をしていないので分からない。

## 測っていないもの

- 深度と RGB の重なりの、画像の左側と、0.4 m より遠い場面での確認
- 参照画像の anchor が示す距離の正しさ（物差しとの比較）
- 連続運転の時間と熱の状態の関係。冷えた状態から `serious` に達するまでの時間と、`nominal` へ戻るまでの時間は測っていない
- `serious` のあいだに、送った実績が上限の半分を下回る原因
